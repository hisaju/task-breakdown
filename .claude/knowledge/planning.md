# エピック分解の知見

- 初回分解は 10 子 → plan-critic と UX 再点検で 17 子 → 人間判断で 6 子に統合して完走した。画面モックの整備のような「見た目・導線」のエピックは、画面単位（基盤／共通部品／画面ごと／横断検査）で束ねると子間の受け渡しが少なく済む（#5, 2026-10-25）
- plan-critic が拾った落穂の型: 画面間のサンプルデータ整合（一覧の n/m と詳細の件数）、no-op ボタンの扱い方針、`data-*` 属性の付与側 AC 漏れ、定数サンプルの日跨ぎ。画面系エピックの分解時は最初からこの 4 点を AC に入れる（#5, 2026-10-25）
- 「一般的な UX として見ておかしいもの」を intent に明示すると、分解時に期限入力欠落・戻る導線重複・ログアウト直リンク等を拾えた。画面系エピックでは intent に必ず入れる（#5, 2026-10-25）
- 子の差分が 500 行を超えたら同じ Issue のまま前半／後半 PR に分ける運用で問題なかった（前半 `Refs`、後半 `Closes`）。L 規模の子は最初から分割前提で計画してよい（#8, 2026-10-25）
- レビューの申し送りは、後続の子 Issue にコメントで AC として追記すると取りこぼしが出なかった（各子の developer が `gh issue view --comments` で読む）（#5, 2026-10-25）
- epic ブランチ向けの子 PR の `Closes #n` は Issue を閉じない。統合 PR の本文に全子の `Closes` を並べて main マージ時に一括クローズする（#19, 2026-10-25）
